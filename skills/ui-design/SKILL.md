# UI設計・実装ガイド

利用者が行う操作を基準に、プロジェクト固有の設計方針、実装、確認結果を一致させる。既存の資料・共通部品・テーマを調べ、依頼を満たす最小の変更を完成させる。

## 依頼に合わせて範囲を決める

| 依頼 | 完成させるもの |
| --- | --- |
| 設計方針・設計資料を整える | 既存のUI設計資料を更新する。適切な資料がなければ短い設計資料を作り、必要な参照を追加する。 |
| 画面を作る・直す・改善する | 対象のUIを実装し、関係する操作・表示を確認する。共通方針が変わる場合は資料も更新する。 |
| 評価・調査・レビューだけ | 根拠のある指摘と改善案を返す。コード・設計資料・設定は変更しない。 |

依頼と直前の文脈から、対象がWeb画面か、利用者のどの作業に関わるかを判断する。画面とAPIなどをまたぐ依頼では、本スキルを画面側に適用し、それ以外の依頼範囲も通常の手順で完了する。表示に現れた不具合の原因が内部処理だと分かったら、画面改修を追加せず原因の層で扱う。

最新の明示依頼を優先する。このスキル自体を、ライブラリ移行、全画面の改修、公開や外部書き込みの許可として扱わない。既に許可された可逆作業は進め、形式的な承認待ちを増やさない。

## 1. 実物と目的を確認する

変更や判断に関係する範囲で、次を調べる。

- 適用される `AGENTS.md`、既存差分、UI設計資料、画面の要件。
- 対象のルート・画面、共通部品、テーマ／デザイントークン、依存関係と版、既存の検証手段。
- 誰が、どの端末で、何を判断・入力・比較・更新するか。会話や資料にある答えを再質問しない。
- 利用可能な画面画像・実際の表示。コードだけから見た目や操作性の検証済みを主張しない。

既存コードは現状の証拠として扱う。現行UIに欠陥がある場合、欠陥をそのまま設計規約にしない。仕様と実装の食い違いを、今回の要件と根拠に照らして判断する。実物にアクセスできない場合は、提供資料から作れる成果物まで進め、未確認箇所を明記する。

## 2. 今回必要な設計判断をする

以下から依頼に関係するものだけを扱う。

- **情報と操作**：利用者の主な作業、情報の優先順位、操作名、比較に必要な情報、誤操作と復帰。
- **画面幅**：PCとスマートフォンで作業の優先度を決める。CSSで縮小・非表示にするだけで重要な情報や操作への到達を失わせない。表からカードへの変換などを一律に要求しない。
- **部品と見た目**：共通部品、意味別の色、文字の階層、余白、数値・日時・単位の表示を既存体系に合わせる。
- **操作中の状態**：対象機能に存在する読み込み、空、検索結果なし、入力エラー、通信失敗、保存中・完了を利用者が区別できるようにする。
- **アクセシビリティ**：ラベル、キーボード操作、フォーカス、文字の読みやすさ、タップ領域、色以外の状態表示を確認する。

新たに補う設計判断は「今回の採用案」などとして既存要件と区別する。推測した利用者像、画像、トークン値、部品APIを既存事実として記載しない。大きな選択がある場合だけ、現状の継続を含む現実的な候補を比較する。

## 3. 設計方針を必要な場所に残す

設計資料の整備を依頼された場合、または実装で継続的に使う共通方針を変更する場合は、[設計資料の作り方](references/project-guide.md)を読む。

既存のUIガイドや設計書内の該当節を正本として使う。名前だけを理由に新たな `DESIGN.md` を増やさない。設計判断のない小さな修正では新規資料を作らない。資料には現行の方針と定義場所を残し、全画面の仕様や作業履歴を蓄積しない。

## 4. 既存の実装に合わせて作る

- 導入済みの部品・トークンを再利用する。共通部品の変更では関連する利用箇所も確認する。
- ライブラリ固有の作業で、対応する公式Skillが利用可能なら使う。未導入の場合は必要な公式資料で補う。Skillがないことだけを理由に停止しない。
- shadcn-svelte、daisyUIなどを固定の必須条件にしない。既存構成で満たせる場合は依存を増やさない。Svelte向け実装にReact専用のAPIやMCP手順を混ぜない。
- 外部資料が必要な場合は[公式資料の選び方](references/sources.md)を参照する。導入版との互換性を確かめ、無関係な資料を一括で読み込まない。
- 実装を依頼された場合は、設計資料の作成だけで終えず、対象のコード変更と必要な確認まで進める。

## 5. 変更に対応する確認をする

リポジトリにある検証手段から、今回の失敗を発見できるものを選ぶ。型検査・ビルド・対象テストの実行範囲は変更とリスクに合わせる。文書だけの変更では参照先と内容の整合を確認し、無関係なアプリ試験を増やさない。

表示や操作を変えた場合は、利用可能な環境で対象画面を開き、関係する幅、操作、状態を確認する。見た目の変更では表示を、振る舞いの変更では操作結果を確認する。スクリーンショットだけで操作の成功を判定しない。ブラウザーや実行環境がなければ、可能な確認を済ませ、視覚・操作確認は未実施と報告する。

成功条件を確認できたら終了する。確認結果に新たな問題がなければ、試験や設計範囲を拡大しない。

## 完了報告

実装・資料整備では「何が変わったか／重要な判断／実施した確認／残る制約」を必要量だけ返す。レビューでは重大な指摘から、根拠、影響、最小の改善案を返す。変更済み・提案・未確認を区別し、未実施の確認を成功扱いにしない。

例：「この工事一覧、現場で開くと肝心の更新日時が見えない。直して」なら、対象一覧の狭い幅での表示を確認し、更新日時に到達できるように修正して検証する。「原因だけ見て」なら確認結果を返し、編集しない。
