# プロジェクトのUI設計資料

設計資料の新規作成・更新が必要なときだけ読む。

## 配置と内容

1. 既存の設計書・UIガイド・関連節を探し、その場所を正本として維持する。
2. 適切な資料がない場合、既存の文書構成に合わせて `docs/DESIGN.md` など一つの資料を作る。
3. 以下の内容から必要なものだけを記載する。ひな型の空欄や仮のパスを残したまま完成扱いにしない。

| 記載する内容 | 書く粒度 |
| --- | --- |
| 利用者と主要な作業 | PC・スマートフォンで何を確認・比較・入力するか。根拠のない人物像を作らない。 |
| 現行の実装と参照先 | 確認できた共通部品、トークン定義、設定、依存版の参照先。値やAPI全文は転記しない。 |
| 採用する共通方針 | 情報の優先順位、部品の選び方、色・文字・余白、状態と操作、小画面の方針。 |
| 完了の判断基準 | 対象の表示・操作をどう確認するか。実行したかどうかとは区別する。 |
| 結論を左右する未確認事項 | 実装との矛盾や、確認が必要な前提だけを短く記す。 |

新たに提案・採用する内容は、既存要件・確認済み事実と分けて書く。依頼の範囲で決められる可逆的な事項は判断して進める。利用者の新たな明示指示で方針が変わった場合は該当箇所を書き換える。実装上の欠陥を正当化するために要件を弱めない。

具体性は観測可能な動作で示す。「わかりやすくする」なら「選択中の絞り込み条件と解除操作を確認できるようにする」まで書く。各画面だけの詳細は、その画面の要件や今回の依頼で扱う。

## AGENTS.mdからの参照

継続利用のための設計資料や作業ルールを整備する依頼では、該当する既存のUI作業ルールに、適用条件と設計書の参照先をまとめる。同等の記述があればそのまま使い、節を重複させない。個別画面の修正やレビューだけなら、作業ルールは追加しない。

例えば正本が `docs/DESIGN.md` の場合：

```markdown
## UI作業
- Web画面の表示・操作を設計、変更、レビューするときは、利用可能なら `ui-design` スキルを使う。利用者によるスキル名の指定は不要。
- 作業前に `docs/DESIGN.md` の関連箇所と対象の既存実装を確認する。この資料はスキル未導入の環境でも参照する。
- 共通の設計方針を変更した場合は、同じ変更で設計資料も更新する。
```

実際の正本が `docs/ui-guidelines.md` などなら、そのパスを使う。`DESIGN.md` を置くだけでは特別な自動読み込みは生じないため、作業条件と参照先を普通の文章で指定する。全作業で全設計書を読む規則にしない。

利用するエージェントに既存の指示ファイルがある場合は、その規約に合わせる。Skill本体を `AGENTS.md` に複製せず、特定Skillの導入を資料参照の必須条件にしない。

## 保存するものの分担

- Skill：プロジェクトをまたいで使う作業手順。
- プロジェクトの設計資料：そのプロジェクトで採用する現在の方針。
- コードと設定：実際の値、部品のAPI、依存版。
- 依頼文や既存タスク資料：今回だけの具体的な要件。

今回の依頼がレビューだけなら、資料への修正案は回答に示し、ファイルへは書き込まない。
